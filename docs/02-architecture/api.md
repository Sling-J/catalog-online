# Контракт API: соглашения

Сам контракт — [`packages/contract/openapi.yaml`](../../packages/contract/openapi.yaml) (OpenAPI 3.1), источник правды ([ADR 0001](adr/0001-stack.md)). Из него Hey API генерирует код для фронтов и бэка. Линтер: `npx @redocly/cli lint` в `packages/contract` (правила — `redocly.yaml`).

## Решения (2026-11-01)
| # | Вопрос | Решение |
|---|---|---|
| API1 | Разделение | Два префикса: `/v1/storefront/{subdomain}/…` — публично, без входа; `/v1/admin/…` — только с сессией, магазин берётся из сессии, не из адреса. Плюс `/v1/auth/…` и `/v1/staff/…` |
| API2 | Загрузка файлов | Напрямую в хранилище: `POST /v1/admin/uploads` даёт короткоживущую ссылку → файл уходит `PUT` в S3/MinIO → `uploadId` передаётся в нужный запрос (фото, логотип, импорт). Уточнения T-405 — ниже, «Загрузки и хранилище» |
| API3 | Длинные списки | Курсор: `?cursor=…&limit=…` → `{ items, nextCursor }`, `nextCursor: null` — конец. Список товаров админки отдаёт ещё `total` — для «Показано N из M» (2026-11-02, T-305) |
| API4 | Ошибки | RFC 9457 `application/problem+json` с машинным `code` и ошибками по полям `errors[]`; текст показывает фронт через Lingui по коду |

## Прочие соглашения
- **Версия** в пути: `/v1`. Ломающие изменения — `/v2`, старое живёт, пока фронты не переедут.
- **Имена** полей — camelCase; `operationId` — глагол + сущность (`listProducts`), из них генерируются имена хуков.
- **Деньги** — целые тенге. **Время** — ISO 8601 UTC. **Id** — UUID v7. Товар на витрине ищется по `shortId`.
- **Частичное обновление** — `PATCH` с переданными полями. **Таблицы целиком** (варианты, значения свойств, порядок категорий и фото) — `PUT` полным списком: так устроены редакторы в админке.
- **Фоновые операции** (импорт, сжатие фото) отвечают `202` / статусом в объекте; фронт опрашивает `GET`.
  > Примечание (2026-11-05, T-307, с согласия основателя): фото товара прикрепляются сразу (`addProductPhoto` → `status: processing`, админка перечитывает товар раз в 2 с, пока есть `processing`); у нового товара — полем `photoUploadIds` в `createProduct` (уже загруженные `product_photo`, по порядку, до 10): товара ещё нет, а прикреплять по одному после создания — риск товара с частью фото.
- **Вход:** cookie `sid` (HttpOnly, Secure, SameSite=Lax, родительский домен). Изменяющие запросы обязаны слать заголовок `X-Requested-With` — простая защита от CSRF. Суперадминка — отдельный cookie `staff_sid`.
  > Примечание (2026-11-09, T-403, решения основателя): вход живёт 30 дней и продлевается при заходе (не чаще раза в сутки); ссылка подтверждения почты — 48 часов, сброса пароля — 1 час, новое письмо гасит прежние ссылки; после сброса пароля закрываются все сессии, после смены — все, кроме текущей. Заблокированный магазин входит (FR-S2). Ограничения частоты с одного IP: вход — 10 в минуту, регистрация — 10 в час, «Ещё раз» — 3 за 15 минут, «Забыли пароль» — 5 за 15 минут. Письма в разработке — в лог API, в продакшене — SMTP (`SMTP_URL`).
- **Ограничение частоты** на вход, регистрацию, письма и события витрины — ответ `429` с `Retry-After`.
  > Примечание (2026-11-09, T-401, решение основателя): кроме строгих ограничений на этих адресах — общий потолок 300 запросов в минуту с IP на любой адрес. Служебный `GET /health` (API жив и видит базу) — вне контракта и без ограничения.
- **Ссылки из писем** (2026-11-02, T-302): ведут в админку — подтверждение почты `https://app.<домен>/verify-email?token=…` (→ `POST /v1/auth/email/verify`), новый пароль `https://app.<домен>/reset-password?token=…` (→ `POST /v1/auth/password/reset`). Устаревший токен — `410 token_expired`, админка показывает «Ссылка устарела».
- **Превью неопубликованной витрины** (A7): `POST /v1/admin/preview-token` → токен в `?preview=` у запросов витрины.
  > Примечание (2026-11-09, T-404, решение основателя): токен без таблицы — внутри магазин и срок (30 минут), подпись HMAC-SHA256 секретом `APP_SECRET` (`core/auth/preview-token.ts`); витрина проверяет подпись и срок (T-410). Выдаётся и заблокированному магазину — его витрина не покажет и по токену.
- **Загрузки и хранилище** (2026-11-09, T-405, решение основателя): два хранилища — публичное (готовые фото и логотипы, постоянные адреса `S3_PUBLIC_URL/<ключ>`, кеш на год) и закрытое (исходники фото и файлы импорта, только для API). Ссылка на загрузку — 10 минут, в закрытое хранилище по ключу `uploads/<магазин>/<загрузка>.<расширение>`; тип и размер входят в подпись — другой файл хранилище не примет. Фото и логотип — JPEG, PNG, WebP, HEIC до 15 МБ, импорт — `.xlsx` или `text/csv` до 20 МБ (иначе 422 по полям `contentType` / `size`). `uploadId` принимается один раз, только своим магазином, по назначению и если файл правда в хранилище, иначе 422 `upload_not_found`.
- **Импорт** (2026-11-10, T-409, решения основателя):
  - **Шаги**: `createImport` (202, `parsing`) → файл читается в фоне → `mapping` (заголовки не узнали) или сразу `previewing` → `previewed` → `applyImport` (202, `applying`) → `done`; концы — `failed` (с `failureCode`) и `cancelled`. Админка опрашивает `getImport`. Незаконченный импорт у магазина один — второй `createImport` отвечает 409 `import_in_progress` (загрузка при этом не тратится). Действие не по статусу — 409 `import_not_ready`: применить можно только из `previewed`, сменить колонки — из `mapping` и `previewed`, отменить — пока не `applying`. Отменённый и упавший остаются в истории.
  - **Файл**: `.xlsx` (первый лист) или CSV — UTF-8, UTF-16 или Windows-1251, разделитель `;`, `,` или табуляция; формат определяется по содержимому. Заголовки — первая непустая строка; колонки без заголовка и пустые строки отбрасываются, повтор заголовка получает номер («Цена (2)»). До 20 000 строк с данными и 60 колонок. `failureCode`: `unreadable_file`, `no_required_columns` (меньше четырёх колонок), `no_rows`, `too_many_rows`, `internal_error` (сбой у нас после всех повторов).
  - **Колонки**: четыре обязательные названы как в шаблоне («Артикул», «Название», «Цена», «Остаток») — шаг «Колонки» пропускается, остальные колонки шаблона — по именам, прочие — свойства (FR-A3). Иначе API предлагает сопоставление по синонимам учётных программ («Номенклатура», «Количество», «Цена розничная»…) и ждёт `setImportMapping`. Его ошибки — 422: `mapping` `missing_required` / `duplicate_target` (как в моках), `mapping.N.column` `not_found` / `duplicate`, `mapping.N.attributeName` `duplicate` / `too_long`. Колонки, не упомянутые в запросе, не загружаются; свойство без имени называется по заголовку. Выбор запоминается по набору заголовков (порядок колонок не важен): следующий такой файл идёт сразу к проверке с `mappingRemembered: true`.
  - **Строки**: у строки одна (первая) ошибка, такая строка пропускается; `preview.errors` и `result.skipped` — число таких строк. Повтор артикула в файле — ошибка второй и следующих строк. Цена — целые тенге: пробелы, «18 900,00», «18,900.50 ₸», копейки округляются. Остаток — целое: «3,000» (так пишет 1С) — три, дробный округляется вниз, отрицательный считается нулём. Категория — путь через «/», глубже двух уровней берутся первые два; несуществующие категории и свойства создаются при применении. Длины — как у полей в контракте, иначе `too_long`.
  - **Применение** — одной транзакцией, пачками; план строится заново по состоянию магазина на этот момент (между проверкой и применением товары могли поправить). Артикул есть — обновляются цена, остаток, штрихкод (если в файле не пусто) и свойства с непустой ячейкой. Артикула нет — вариант добавляется в товар своей группы («Код товара», а без него — название без учёта регистра): товар с таким ключом; иначе товар, где уже лежит другой артикул этой группы; иначе новый товар. Описание импорт пишет только новому товару.
  - **Пометки «из Excel»** (`importedFields`): новый товар получает `name`, `variants` и, если колонка категории сопоставлена, `category`. Название и категорию существующего товара импорт меняет, только пока на поле стоит пометка; ручная правка (`updateProduct`, массовая смена категории) её снимает — и поле остаётся за человеком. Товар, заведённый руками, при совпадении артикула получает только `variants`.
  - **«Нет в файле»** (`zeroMissing`, `preview.missingInFile`): только варианты товаров с пометкой `variants`, у которых остаток больше нуля. Товары, заведённые руками, импорт не обнуляет. Артикул строки с ошибкой считается присутствующим в файле.
  - **Сбои**: фоновые шаги повторяются до трёх раз; каждый проверяет статус и пишет результат условным переходом, поэтому повтор и отмена ничего не задваивают. Строки между проверкой и применением лежат в `import_rows` и удаляются после `done` / `failed` / отмены; ошибки по строкам остаются для истории.
- **Категории и свойства** (2026-11-09, T-408, решения основателя):
  - Поведение — как в моках T-311 (`@catalog/contract/fixtures`, `admin-catalog.ts`). Категории: новая — в конец своего уровня; родитель — только категория верхнего уровня (иначе 422 `parentId` `too_deep`, нет такой — `not_found`); повтор имени среди соседей без учёта регистра — 409 `category_name_taken`. `PUT /categories/order` — ровно все категории магазина по разу (иначе 422 `items` `invalid_value`); неверный родитель или вложение категории с подкатегориями — 422 `items.N.parentId` `invalid_value`; повтор имени у новых соседей — 422 `items.N.id` `duplicate`; позиции внутри родителя пересчитываются подряд (равные — по порядку в запросе). `productCount` — только собственные товары категории. Путь `Девочки / Куртки` (`categories.path`, для импорта) пересчитывается при переименовании и переносе.
  - Свойства: новое — в конец; значения при создании без повторов (лишние молча отбрасываются); повтор имени — 409 `attribute_name_taken`. `PUT …/values`: пустое значение, чужой или повторённый id — 422 по ячейке (`values.N.value` `required`, `values.N.id` `not_found` / `duplicate`); повтор значения — 409 `attribute_value_taken` с `values.N.value` `taken`; удаление значения, которое стоит у вариантов, — 409 `attribute_value_in_use`. Переименование значения или свойства видно в вариантах сразу (варианты хранят ссылку, не текст).
  - **Удаление свойства** снимает его значения с вариантов, даже если варианты товара после этого совпадут («Красный 104» и «Синий 104» → два «104»): повтор покажет таблица размеров при следующем сохранении (решение основателя 2026-11-09).
  - **Размер списков** в контракте: `PUT /categories/order` — до 500 элементов, значения свойства (`createAttribute`, `PUT …/values`) — до 200 (решение основателя 2026-11-09).
  - Правки категорий (и отдельно свойств) одного магазина идут по очереди — блокировка на время транзакции; «Свой размер» из таблицы размеров берёт ту же блокировку свойств.
- **Товары** (2026-11-09, T-407, решения основателя):
  - **Курсор** — закладка «после этой строки»: значение порядка и id последней строки, base64url; второй ключ порядка — id, поэтому равные цены и остатки идут стабильно. Курсор от другого `sort` или испорченный — 422 по полю `cursor`. Помощник — `core/pagination`, им же пользуется витрина (T-410).
  - **Поиск** `q` — «содержит» без учёта регистра по названию, артикулу и штрихкоду; `%` и `_` — обычные символы. Индекса для нечёткого поиска пока нет. Вкладка «Без фото» — у товара нет ни одного фото (и обрабатываемого); «Цена» в списке и порядке — минимальная цена вариантов.
  - **Адрес**: `slug` — транслитерация названия (русские и казахские буквы, своя функция), меняется при переименовании; `shortId` — 5 символов base36, не меняется.
  - **Таблица размеров** (`PUT …/variants`, `createProduct`): строка с id обновляется, без id создаётся, остальные удаляются; значение свойства по тексту без учёта регистра, нового («Свой размер») — создаётся в конце свойства. Ошибки по ячейкам (422): повтор id, артикула или набора размеров, одно свойство дважды в строке, пустое значение, чужое свойство (`not_found`), id варианта другого товара. Артикул другого товара — 409 `sku_taken` (без ошибок по полям). Пустой артикул: у новой строки — `<КОД ТОВАРА>-<n>` (`7F3K2-1`, занятые пропускаются), у существующей — остаётся прежний. «Цена от–до» и «всего на складе» товара пересчитываются в той же транзакции.
  - **Фото**: не больше 10 (409 `photo_limit_reached`); сжатие ставится в той же транзакции, что и запись; новый порядок — ровно все фото товара, иначе 422 по `photoIds`; после удаления позиции идут без пропусков; файлы удалённых фото и товара стираются сразу после записи (сбой хранилища — в лог). Обложка в списке — первое фото, пока оно сжимается — `null`.
  - **Прочее**: несуществующий, чужой или не-UUID id в адресе — 404; чужая категория — 422 по `categoryId`; массовые действия пропускают чужие id и возвращают число изменённых; `set_category` без `categoryId` — 422. ~~Пометки «из Excel» (`importedFields`) ручная правка не меняет — решится в T-409.~~ С T-409 название и категория, изменённые руками, теряют пометку — см. «Импорт» ниже.
- **Картинки** (2026-11-09, T-406, решения основателя): фото товаров и логотип сжимаются в три WebP по ширине 320 / 640 / 1280 (маленькие не увеличиваются, высота не больше двух ширин), с поворотом по EXIF, без метаданных (EXIF и GPS не попадают на витрину); `width` / `height` в `Image` — стороны исходника после поворота. Готовые файлы — в публичном хранилище: `shops/<магазин>/photos/<фото>/<ширина>.webp`, `shops/<магазин>/logo/<загрузка>/<ширина>.webp`. HEIC с iPhone открывается (`heic-decode`, ADR 0001). **Логотип** (`setShopLogo`) сжимается сразу в запросе и приходит в ответе; файл не открывается как картинка — 422 `image_unreadable`, логотип прежний; при замене и удалении файлы прежнего (размеры и исходник) удаляются. **Фото товара** — фоновая задача `photos.process` (ставится в T-407 вместе с записью фото): `processing` → `ready`; не картинка — сразу `failed`; другой сбой — ещё две попытки с паузой, затем `failed`. Брошенные загрузки (не использованы сутки после конца ссылки) убираются раз в сутки, в 02:30 по Алматы.
- **Магазин** (2026-11-09, T-404): публикация — 409 `shop_not_ready`, если нет названия, адреса витрины, WhatsApp, видимого товара или почта не подтверждена (A9); 409 `shop_blocked` — магазин заблокирован. Снятие с публикации не меняет статус заблокированного и черновика. Адрес витрины: формат — 422, служебное слово — 409 `subdomain_reserved` (список — `modules/shop/lib/subdomain.ts`), занят — 409 `subdomain_taken`; `checkSubdomain` неверный формат отдаёт ответом `reason: invalid`, свой адрес — свободен. Закрытие в графике — позже открытия, `00:00` — до конца дня (422 `schedule.<день>.close`). Пустой необязательный текст в `PATCH /shop` очищает поле. Загрузка логотипа — в T-406 (до неё `PUT /shop/logo` отвечает 422 `upload_not_found`).
  > Примечание (2026-11-02, T-113): несохранённые правки админка передаёт витрине через `postMessage`; формат сообщений — `packages/contract/src/preview.ts` (`@catalog/contract/preview`), описание — `04-design/storefront.md`, «Превью из админки». `PreviewToken` добавлен и в `checkStorefrontCart`.

## Уточнения контракта (2026-11-08, решение основателя)
Закрывают вопросы из [open-questions.md](../open-questions.md), заданные при работе на моках.
- **`checkStorefrontCart`** отвечает только `ok` / `out_of_stock` / `unavailable` с текущими `price` и `quantity` (урезанным до остатка). Статусов `price_changed`, `quantity_reduced` и поля `previousPrice` нет: API не знает, что лежит в корзине покупателя, а доверять цене от клиента незачем. «Цена изменилась» и «количество уменьшено» витрина определяет сама, сравнивая ответ со снимком корзины (T-107).
- **410 на `getStorefrontShop`** (скрытый или заблокированный магазин) — с телом `StorefrontShopGone`: Problem + `shop` (название, логотип, WhatsApp, адрес, график) для экрана «Каталог скрыт». Отдельного запроса контактов нет.
- **`Import.rowCount`** — число строк данных в файле; API заполняет его сразу после чтения файла (до сопоставления колонок), до этого `null`. Показывается на шаге «Колонки».
