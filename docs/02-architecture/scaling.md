# Узкие места и масштабирование бэкенда

Аудит `apps/api` после E4 (2026-11-11, по коду на коммите `2b95262`). Здесь собрано, где мы сознательно сделали «пока так», когда это станет проблемой и что тогда делать. Это **не план работ**: строка становится задачей в [backlog.md](../05-tasks/backlog.md), когда сработал её признак или основатель решил сделать её заранее (тогда в задаче — ссылка на номер строки, например «SC7»).

Стек — [ADR 0001](adr/0001-stack.md), структура кода — [backend-structure.md](backend-structure.md), соглашения API — [api.md](api.md).

**Принцип** ([ADR 0004](adr/0004-backend-structure.md)): с ИИ дешевеет написание кода, но не владение системой. Каждая новая часть (Redis, брокер, поисковый движок) — это ещё один сервис, который нужно обновлять, бэкапить, мониторить и который может упасть. Поэтому порядок всегда один: сначала решаем средствами, которые уже есть (PostgreSQL, процесс Node, заголовки HTTP), новую часть берём, когда без неё уже нельзя. Написать переход потом — «один промт»; содержать лишний сервис с первого дня — постоянная цена.

## 1. Как устроено сейчас

```
браузер ──► Caddy ──► web (TanStack Start, SSR) ──► api
                 └──► admin (статика) ─────────────► api
браузер ──PUT по подписанной ссылке──► SC3 закрытое (исходники фото, файлы импорта)
браузер ◄──GET напрямую (кеш на год)── SC3 публичное (готовые фото и логотипы)

api — один процесс Node:
  • HTTP: NestJS на Express, 60 эндпоинтов
  • фоновые задачи pg-boss — в этом же процессе: photos.process, imports.parse / preview / apply, uploads.cleanup (раз в сутки)
  • чтение файла импорта — в отдельном потоке (worker_threads, ≤ 512 МБ, ≤ 60 с)
  ├──► PostgreSQL: данные, сессии, очередь pg-boss (схема pgboss), счётчики статистики
  ├──► SC3 (оба хранилища)
  └──► SMTP (письма)
```

| Связь | Как | Что важно |
|---|---|---|
| api ↔ PostgreSQL | `postgres.js` (пул по умолчанию — 10 подключений) + отдельный пул pg-boss (4) | всё состояние — в базе, кроме счётчиков ограничения частоты (SC5) |
| api → очередь | `jobs.send(задача, данные, tx)` в той же транзакции, что и запись | задача не потеряется и не появится лишней при откате — главное свойство, ради которого pg-boss |
| файлы | прямо из браузера в SC3 по подписанной ссылке, в API — только `uploadId` | файл через API не проходит ни при загрузке, ни при отдаче |
| api → SMTP | прямо в запросе (`sendSafely`) | SC6 |
| api → SC3 при картинках | исходник целиком в память, сжатие sharp, HEIC — `heic-decode` | SC2, SC3 |

Без изменений кода API уже можно запустить в нескольких экземплярах (сессии в базе, очередь pg-boss с `SKIP LOCKED`, расписание pg-boss работает в кластере). Сломается только ограничение частоты (SC5).

## 2. Два вопроса основателя

### 2.1. Импорт файла и брокер сообщений (Kafka / RabbitMQ)

**Как на самом деле устроено.** Файл импорта через эндпоинт не идёт: админка получает подписанную ссылку (`POST /v1/admin/uploads`), кладёт файл прямо в SC3, а `createImport` принимает только `uploadId` и отвечает 202. Читает файл фоновая задача `imports.parse`. «300 МБ после распаковки» — это про `.xlsx`: это zip, и «вредная» книга может распаковаться в гигабайты. Поэтому чтение идёт в отдельном потоке с потолком памяти 512 МБ и временем 60 с; такой файл убивает только поток, импорт получает `failed` / `too_large` (`api.md`, «Импорт»).

**Что остаётся настоящей проблемой.** Фоновые задачи работают **в том же процессе и контейнере, что и HTTP** (решение 4 в [backend-structure.md](backend-structure.md), раздел 15). Значит:
- пик памяти контейнера API = память API + до 512 МБ потока чтения + буферы фото;
- сжатие фото и разбор импорта делят с запросами покупателей процессор и пул потоков libuv;
- HEIC декодируется прямо в основном потоке и на это время останавливает все запросы (SC2).

**Нужен ли брокер.** Нет — брокер у нас уже есть: pg-boss и есть очередь задач, только живёт в PostgreSQL.

| | pg-boss (сейчас) | RabbitMQ | Kafka |
|---|---|---|---|
| Что это | очередь задач в таблицах PostgreSQL | брокер сообщений: очереди, маршрутизация, подтверждения | распределённый журнал событий: хранит поток, читатели идут по нему со своей позиции |
| Для чего создан | фоновые задачи приложения | задачи и сообщения между сервисами | потоки событий в сотни тысяч в секунду, аналитика, связь десятков сервисов |
| Задача в одной транзакции с данными | да, из коробки | нет — нужен «transactional outbox»: таблица в базе + отдельный пересыльщик, то есть ровно то, что делает pg-boss | нет — тот же outbox |
| Новый сервис в системе | нет | да (кластер, мониторинг, бэкап настроек) | да, самый тяжёлый в эксплуатации |
| Наш объём | сотни задач в день на пилоте, тысячи — на 100 магазинах | — | — |

**Что делать, по шагам:**
1. **Отдельный процесс задач** (SC1): точка входа `worker.ts` из того же кода и образа, в API задачи не обрабатываются, только ставятся. Это закрывает исходную тревогу: тяжёлое уходит из процесса, отвечающего на запросы. ADR 0001 так и рисовал инфраструктуру (контейнер `worker`), ADR 0004 отложил ради простоты.
2. **Свои лимиты процессу задач:** память контейнера, `localConcurrency`, при росте — отдельный сервер.
3. **Брокер — только если:** устойчиво больше ~100 задач в секунду и опрос очереди заметно грузит базу; или появились потребители на другом языке или в отдельных сервисах. Тогда — RabbitMQ (это задачи, а не поток событий) с outbox-таблицей. Kafka для этого продукта не нужна ни в одном видимом сценарии: потока событий такого объёма у каталога малых магазинов нет; даже статистика витрины решается счётчиками (SC7).

### 2.2. Фасеты витрины в памяти

**Решение (основатель, 2026-11-10, `api.md`, «Фасеты»):** считаем в памяти, пока не тормозит; начнёт тормозить — переводим в SQL целиком.

**Замер (2026-11-11, Node 22.20, синтетические данные, только `computeFacets`, без базы):**

| Варианты в наличии | Свойства в фильтрах × значения | Время счёта |
|---|---|---|
| 2 000 | 4 × 10 | 0,5–0,6 мс |
| 20 000 (потолок NFR-3) | 6 × 20 | 4–7 мс |

Сам счёт дешёвый, но эти 4–7 мс блокируют процесс: при 50 запросах фасетов в секунду к большому магазину — треть ядра. **Не замерено и, вероятно, дороже:** SQL выбирает все варианты в наличии под категорию и поиск (до 20 000 строк с `array_agg`) и гонит их в Node на каждый запрос.

**Признак:** p95 `getStorefrontFacets` дольше 200 мс или магазин больше ~5 000 вариантов с заметным трафиком. Проверяем в T-606 (скорость витрины).

**Что тогда, по порядку:**
1. Кеш результата по ключу «магазин + версия каталога + запрос» (SC8): каталог магазина меняется редко, а покупатели жмут одни и те же фильтры. Скорее всего, этого хватит надолго.
2. Счёт целиком в SQL: по запросу на свойство с `count(distinct product_id)` и условием «все фильтры, кроме этого свойства» (или один запрос с `GROUPING SETS`), цена — `min` / `max` с фильтрами без цены. Правила те же, юнит-тесты `facets.ts` переносятся в e2e.
3. Если и этого мало — заранее посчитанная таблица «значение → товары в наличии» на магазин, пересчёт фоновой задачей при изменении каталога.

## 3. Реестр

Срочность: **до пилота** — сделать в E6 до первых магазинов (рекомендация, ждёт решения основателя); **по признаку** — когда сработает признак; **при росте** — когда понадобится больше одного экземпляра API или сотни магазинов.

## 4. Когда понадобятся Redis и брокер

| Нужда | Сейчас | Redis нужен, когда |
|---|---|---|
| Ограничение частоты на несколько экземпляров (SC5) | память процесса → PostgreSQL | запросов столько, что таблица счётчиков заметно грузит базу |
| Общий кеш витрины (SC8) | заголовки HTTP + память процесса | экземпляров API больше одного и промахи кеша в каждом из них заметны |
| Счётчики статистики (SC7) | пачки из памяти | несколько экземпляров и потери при падении стали неприемлемы |
| Сессии | PostgreSQL, один индексный запрос | не нужен: запрос дешёвый |
| Очередь задач | pg-boss | не нужен (BullMQ на Redis — только если уйдём с pg-boss, см. 2.1) |

**Правило:** Redis появляется, когда API работает больше чем в одном экземпляре **и** хотя бы две строки таблицы выше упёрлись в базу или память процесса. Тогда он закрывает их все сразу. Брокер (RabbitMQ) — по условиям из 2.1, Kafka — не планируем.

## 5. Что уже сделано правильно — не трогать

- Файлы идут мимо API (подписанные ссылки), публичные картинки — по неизменяемым ключам с кешем на год.
- Задача ставится в той же транзакции, что и данные; задачи повторяемы — статус проверяется условным переходом, повтор ничего не задваивает.
- Чтение файла импорта изолировано в отдельном потоке с потолками памяти и времени.
- Курсорная пагинация везде, где длинные списки (на больших магазинах не замедляется к концу списка, в отличие от `offset`).
- Статистика — счётчики по дням, без сырых событий: таблица растёт медленно, отчёты дешёвые.
- Состояние — в базе: API без изменений запускается в нескольких экземплярах (кроме SC5).
- Контракт проверяется тестами: при переносе фасетов в SQL или кеша поведение ловят существующие e2e.
