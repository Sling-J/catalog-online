# Структура кода бэкенда (`apps/api`)

Правила для `apps/api`. Решение — [ADR 0004](adr/0004-backend-structure.md) (2026-11-08, основатель принял все рекомендации раздела 15). Аналог [frontend-structure.md](frontend-structure.md) для бэка. Раздел 1 — обзор подходов для понимания, почему выбран этот; правила — разделы 2–14.

Стек уже выбран в [ADR 0001](adr/0001-stack.md): NestJS, PostgreSQL + Drizzle, pg-boss, sharp, argon2, сессии в cookie. Контракт — [`openapi.yaml`](../../packages/contract/openapi.yaml), соглашения — [api.md](api.md), таблицы — [data-model.md](data-model.md).

## 0. Структура и архитектура — в чём разница

Это разные уровни одного вопроса «как устроено».

| Уровень | Вопрос | Где у нас решено |
|---|---|---|
| **Архитектура системы** | Из каких частей система: сколько сервисов, какая база, очередь, хранилище, как фронты ходят в API | ADR 0001: один API (монолит), PostgreSQL, очередь pg-boss в той же базе, S3 для файлов, две фронта по контракту |
| **Структура кода (внутренняя архитектура приложения)** | Как внутри `apps/api` разложен код: папки, слои, кто кого может импортировать, где бизнес-правила, где SQL | **этот документ** |

Для фронта второй уровень — FSD. Для бэка нужен свой аналог.

### Почему не «просто как в NestJS»
NestJS даёт **кирпичи**: модули, контроллеры, провайдеры (сервисы), внедрение зависимостей, guards, pipes, фильтры исключений. Документация Nest советует делить приложение на модули по предметной области — **это мы и берём за основу** (раздел 2).

Но Nest не отвечает на вопросы, от которых зависит, будет ли код одинаковым через 13 задач и разных сессий агента:
- где бизнес-правило («опубликовать можно, только если почта подтверждена»), а где SQL;
- как гарантировать, что каждый запрос к данным отфильтрован по магазину (главный риск SaaS — увидеть чужие товары);
- где начинается и кончается транзакция (импорт — одна транзакция на сотни строк);
- как исключения превращаются в `problem+json` с нашими `code`;
- можно ли модулю «Товары» лезть в таблицы модуля «Импорт»;
- как тестировать с базой.

Аналогия с фронтом: React даёт компоненты, но не говорит, где лежит модель корзины, — на это у нас FSD. Здесь так же: Nest — компоненты, документ — правила их раскладки.

## 1. Какие бывают структуры (для изучения)

От простого к сложному. Для каждой — суть, плюсы, минусы и подходит ли нам.

### 1.1. Слоистая по техническим слоям (Layered, «MVC»)
```
src/controllers/  products.controller.ts, shop.controller.ts …
src/services/     products.service.ts, shop.service.ts …
src/repositories/ …
```
- **Суть:** папка на каждый технический слой, внутри — все сущности вперемешку.
- **Плюсы:** проще некуда, понятно с первого взгляда.
- **Минусы:** одна фича размазана по трём-четырём папкам; через год `services/` — 40 файлов, которые все друг друга импортируют. Нет границ между областями.
- **Нам:** нет. Это как на фронте держать `components/`, `hooks/`, `stores/` — от чего FSD и уводит.
- Почитать: Martin Fowler, [Presentation Domain Data Layering](https://martinfowler.com/bliki/PresentationDomainDataLayering.html).

### 1.2. Модули по предметной области (Feature modules, «модульный монолит»)
```
src/modules/products/   controller, service, repository, mapper
src/modules/imports/    …
src/modules/storefront/ …
```
- **Суть:** папка = область (товары, импорт, витрина). Внутри — свои слои. Модули общаются только через то, что явно экспортируют.
- **Плюсы:** всё про фичу в одном месте; границы видны; это родной способ Nest (`@Module`). Можно потом вынести модуль в отдельный сервис, если понадобится (не понадобится).
- **Минусы:** нужно договориться о правилах внутри модуля и между модулями — сам Nest их не навязывает.
- **Нам:** **да, основа** (раздел 2).
- Почитать: [NestJS — Modules](https://docs.nestjs.com/modules); пример большого модульного монолита — [kgrzybek/modular-monolith-with-ddd](https://github.com/kgrzybek/modular-monolith-with-ddd) (на C#, но идея та же; смотреть README, не код).

### 1.3. Чистая / гексагональная / луковая архитектура (Clean, Hexagonal, Onion)
```
domain/         сущности и правила, без Nest и без Drizzle
application/    сценарии (use cases), интерфейсы «портов» (ProductRepository)
infrastructure/ реализации портов: Drizzle, S3, SMTP
interface/      контроллеры
```
- **Суть:** бизнес-логика в центре и ничего не знает о фреймворке и базе; база и HTTP — «адаптеры» снаружи, подключаются через интерфейсы.
- **Плюсы:** логику можно тестировать без базы; базу или фреймворк можно заменить.
- **Минусы:** на каждую сущность — интерфейс, реализация, маппер доменной модели в строку базы и обратно. Для CRUD по готовому контракту это в 2–3 раза больше кода без пользы: менять Postgres или Nest мы не собираемся, а логики, которую стоит изолировать, мало.
- **Нам:** нет целиком. Берём одну идею: чистые функции для сложной логики (разбор импорта, расчёт фасетов) — в отдельных файлах без Nest и базы (раздел 3, `lib/`).
- Почитать: Robert Martin, [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html); Alistair Cockburn, [Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/).

### 1.4. DDD (тактический: агрегаты, объекты-значения, доменные события)
- **Суть:** богатая модель предметной области — правила живут в классах-сущностях («Товар» сам проверяет свои варианты), изменения идут через «агрегаты», между частями — события.
- **Плюсы:** незаменим, когда предметная область сложная и правил сотни (банки, логистика).
- **Минусы:** много понятий и церемоний. У нас область простая: каталог, остатки, настройки.
- **Нам:** нет. Полезное из DDD у нас уже есть — общий словарь ([glossary.md](../glossary.md)) и границы областей = модули.

### 1.5. CQRS (раздельные команды и запросы)
- **Суть:** изменение данных (команды) и чтение (запросы) — разные обработчики, иногда разные модели и даже базы. В Nest есть пакет `@nestjs/cqrs`.
- **Плюсы:** чтение можно оптимизировать отдельно от записи.
- **Минусы:** на каждый запрос — класс команды, класс обработчика, шина. Для нас — лишний слой.
- **Нам:** нет как паттерн. Но сама идея у нас естественно есть: **витрина — отдельный модуль только для чтения** со своими запросами под покупателя (опубликованные, с учётом настроек наличия), а админка пишет. Это и есть «CQRS-lite» без шины.
- Почитать: Martin Fowler, [CQRS](https://martinfowler.com/bliki/CQRS.html).

### 1.6. Вертикальные срезы (Vertical Slice)
```
src/features/products/create-product.ts   // контроллер + проверка + SQL в одном файле
src/features/products/list-products.ts
```
- **Суть:** файл (или папка) на один сценарий/эндпоинт, внутри — всё от HTTP до SQL. Общего мало, дублирование допускается.
- **Плюсы:** очень легко найти код эндпоинта, изменения не задевают соседей. По духу ближе всего к FSD.
- **Минусы:** в Nest непривычно (он любит контроллер на ресурс), общий код (проверка магазина, маппинг товара) начинают копировать. ~60 эндпоинтов = 60 файлов с похожим началом.
- **Нам:** нет как основа, но частично берём: сложный сценарий (импорт, публикация) получает свой файл-сервис внутри модуля, а не раздувает общий.
- Почитать: Jimmy Bogard, [Vertical Slice Architecture](https://www.jimmybogard.com/vertical-slice-architecture/).

### 1.7. Микросервисы
- Отдельные приложения на каждую область со своей базой. Для MVP одного разработчика — только вред (сеть, согласованность, деплой). **Нет**, уже решено в ADR 0001.

## 2. Рекомендация

**Модульный монолит на модулях NestJS (1.2) + тонкие слои внутри модуля: контроллер → сервис → репозиторий (Drizzle).** Плюс три точечных правила из других подходов: чистые функции для сложной логики (из 1.3), витрина — отдельный модуль только для чтения (из 1.5), сложный сценарий — свой сервис (из 1.6).

Почему именно так:
1. **Это родной путь Nest** — меньше всего трения с документацией, примерами и тем, что знает любая модель. Агенту не надо «бороться» с фреймворком.
2. **Ложится на контракт.** Hey API уже генерирует типы контроллеров по тегам контракта (`ProductsControllerMethods`, `ImportsControllerMethods`, …) — один тег = один контроллер = один модуль. Структура задана контрактом, придумывать нечего.
3. **Предсказуемость для Sonnet.** Каждый модуль устроен одинаково, файлы называются одинаково. Задача «сделай модуль категорий по образцу товаров» выполняется копированием образца, без решений.
4. **Изоляция магазинов в одном месте.** SQL только в репозиториях, а каждая функция репозитория обязана принять `shopId` — забыть фильтр сложно, проверить на ревью легко (раздел 5).
5. **Без лишних церемоний.** Нет интерфейсов «на всякий случай», доменных классов и шины команд: CRUD по готовой спеке пишется прямо.

## 3. Раскладка папок

```
apps/api/
  drizzle.config.ts
  drizzle/                     миграции (генерирует drizzle-kit, в git)
  src/
    main.ts                    запуск: Nest, cookie, CORS, фильтр ошибок, логгер
    app.module.ts              подключает core и все модули
    worker.ts                  (позже, если понадобится) отдельный процесс фоновых задач

    core/                      инфраструктура без бизнес-смысла — аналог shared на фронте
      config/                  чтение и проверка переменных окружения (Zod)
      db/
        schema/                таблицы Drizzle по областям: shops.ts, catalog.ts, imports.ts, stats.ts, staff.ts
        db.module.ts           провайдер подключения
        types.ts               Db, Tx — тип «база или транзакция»
      errors/                  AppError, коды, глобальный фильтр → problem+json
      validation/              pipe проверки тела и параметров по схемам Zod из контракта
      context/                 контекст запроса: текущий аккаунт, магазин, сотрудник
      auth/                    guards: сессия магазина, сессия сотрудника, X-Requested-With
      storage/                 S3: подписанные ссылки, ключи, публичные адреса фото
      mail/                    отправка писем (SMTP; в разработке — в лог)
      jobs/                    pg-boss: подключение, регистрация обработчиков
      rate-limit/              ограничение частоты (429 + Retry-After)

    modules/                   предметные области — один модуль на тег контракта
      auth/                    регистрация, вход, сессии, письма, пароли
      shop/                    настройки, адрес, публикация, чек-лист, логотип, preview-токен
      uploads/                 выдача ссылок на загрузку
      products/                товары, варианты, фото, массовые действия, счётчики
      catalog/                 категории и свойства (теги Categories + Attributes)
      imports/                 импорт файлов
      storefront/              публичная витрина — только чтение + cart/check
      stats/                   события и статистика

  test/
    helpers/                   поднять приложение, создать магазин, войти, очистить базу
```

### Внутри модуля (на примере `products/`)
```
modules/products/
  products.module.ts          собирает модуль, объявляет exports
  products.controller.ts      HTTP: implements ProductsControllerMethods
  products.service.ts         бизнес-правила и транзакции
  products.repository.ts      весь SQL модуля (Drizzle)
  products.mapper.ts          строка базы → объект контракта
  product-photos.service.ts   отдельный сценарий, если сервис разрастается (> ~300 строк)
  lib/                        чистые функции без Nest и базы (расчёт min/max цены и т.п.)
  products.e2e.test.ts        тесты эндпоинтов на настоящей базе
  lib/*.test.ts               юнит-тесты чистых функций
  workers/                    обработчики фоновых задач модуля (например, сжатие фото)
```
Не каждый модуль имеет все файлы: нет SQL — нет репозитория, нет сложной логики — нет `lib/`.

> Примечание (2026-11-09, T-401, уточнения по согласованному с основателем плану): в `core` появились ещё `http/` (`configureApp`: CORS, `trust proxy`, логгер — общее для `main.ts` и тестов), `logging/` (nestjs-pino), `health/` (служебный `GET /health` вне контракта) и `core.module.ts`, который подключает всё это и глобальные фильтр, pipe и guards. `AppModule.forRoot(config)` и `CoreModule.forRoot(config)` принимают конфиг аргументом — тесты собирают приложение со своей базой. Точки входа нет в `worker.ts` (не понадобился). Миграций в `drizzle/` нет до T-402.

> Примечание (2026-11-09, T-403): `core/auth` — сессии магазина: `SessionService` (открыть, найти по cookie, продлить, закрыть), guard `@Authenticated()`, SQL сессий — в `core/auth/sessions.repository.ts`. Cookie ставится в ответ через контекст запроса (`RequestContext.response()`, nestjs-cls с `saveRes`), поэтому методы контроллеров совпадают с сигнатурами контракта и не принимают `Response`. `core/mail` — `Mailer` (лог или SMTP), в тестах подменяется. С T-407 `core/pagination` — курсор списков (`encodeCursor` / `decodeCursor`) и `PathIds` для id в адресе (`@Param(PathIds) path` — не UUID → 404). Модуль `products` целиком: `ProductsService` (список, карточка, массовые, счётчики, `readiness` для чек-листа магазина), `ProductVariantsService` (таблица размеров), `ProductPhotosService`; проверка категории и значения свойств («Свой размер») — через сервисы модулей `categories` и `attributes` (с T-408: `CategoriesService.exists`, `AttributesService.existing` / `resolveValues`); зависимость в одну сторону — товары → категории, свойства. Число товаров категории и вариантов у значения модули категорий и свойств считают своими запросами (только чтение чужих таблиц). С T-406 `core/jobs` — `Jobs`: задача объявляется `defineJob<Данные>('имя', { retryLimit, … })` константой в `workers/` модуля, обработчик и расписание регистрируются в `onModuleInit` (`jobs.work`, `jobs.schedule`), ставится `jobs.send(задача, данные, tx)` — с `tx` в той же транзакции; обработчик получает `{ last }` — последняя ли попытка. В e2e очередь в памяти — `t.jobs` (`run`, `drain`), настоящий pg-boss — `createTestApp({ realJobs: true })` (`jobs.e2e.test.ts`). `core/images` — `Images`: `publish` (исходник → три WebP в публичном хранилище), `remove`, `toImage` (адреса для ответа); `pg-boss`, `sharp`, `heic-decode` вне core — только типы (`eslint.api.js`). Модуль `products` пока только с обработкой фото (`ProductPhotosService.process`, задача `PROCESS_PHOTO`). С T-405 `core/storage` — `Storage` (подписанные ссылки, `head`, `get` / `put`, `publicUrl`; в e2e — хранилище в памяти `test/helpers/storage.ts`), модуль `uploads` экспортирует `UploadsService.consume` — им логотип, фото и импорт принимают `uploadId`. С T-404 в `core/auth` ещё `PreviewTokens` — подписанные токены превью витрины (выдаёт модуль магазина, проверит витрина). Помощник тестов `signUp` (`test/helpers/session.ts`) создаёт магазин с сессией прямо в базе — тесты модулей не зависят от лимитов регистрации. Модули импортируют из core `index.ts` папки и ещё схему БД (`core/db/schema/index.ts`) — правило в `eslint.api.js`. Контекст запроса, сессии и почта — глобальные модули Nest.

## 4. Слои и правила зависимостей

```
controller → service → repository → core/db
                  ↘ mapper, lib (чистые функции)
```

| Слой | Делает | Не делает |
|---|---|---|
| **controller** | Принимает запрос, берёт магазин из контекста, вызывает сервис, возвращает результат. `implements <Тег>ControllerMethods` — расхождение с контрактом ломает `tsc` | Никаких `if` с бизнес-смыслом, никакого SQL |
| **service** | Бизнес-правила («нельзя удалить категорию с подкатегориями» → 409), транзакции, вызовы других модулей, постановка фоновых задач | Не знает про HTTP (нет `Request`, `Response`, кодов статуса — только `AppError` с кодом) |
| **repository** | SQL через Drizzle; каждая функция по данным магазина первым аргументом принимает `shopId` и фильтрует по нему | Никаких бизнес-решений и исключений с кодами, кроме «не найдено» → `null` |
| **mapper** | Чистое преобразование строки базы в форму контракта (camelCase, адреса фото, `stock` по настройке магазина) | Запросов к базе |
| **lib** | Чистые функции со сложной логикой: разбор файла импорта, сопоставление колонок, фасеты, курсоры | Импортов Nest и базы — тестируются без них |

### Между модулями
- Модуль использует другой **только через сервис, который тот явно экспортировал** в `@Module({ exports })`. Репозитории наружу не экспортируются.
- Схема Drizzle (`core/db/schema`) общая — её видят все (как `shared`). Но **писать в таблицы чужой области нельзя**: импорт меняет товары через `ProductsService`, а не своим SQL. Исключение — модуль `storefront`: он **только читает** таблицы каталога своими запросами, потому что витрине нужны другие выборки (только опубликованные, наличие по настройке, фасеты).
- Циклов между модулями нет. Если двум модулям нужна общая логика — вынести её в отдельный модуль или `core`.
- `core` не импортирует `modules`.

## 5. Связь с контрактом

- **Контроллер реализует сгенерированный тип:** `class ProductsController implements ProductsControllerMethods`. Параметры пути приходят объектом (`@Param() path`), запроса — объектом (`@Query() query`), тело — `@Body() body`, как в сгенерированных сигнатурах.
- **Магазина в сигнатурах нет** (`getShop: () => Promise<…>`): он не часть контракта, а берётся из сессии. Поэтому текущий аккаунт и магазин лежат в **контексте запроса** (`core/context`, на AsyncLocalStorage через `nestjs-cls`), его заполняет guard сессии. Контроллер достаёт `shopId` из контекста и **явно передаёт в сервис**: `this.products.list(ctx.shopId(), query)`. Сервисы и репозитории контекст не читают — так они проще в тестах и не зависят от «магии».
- **Проверка входных данных** — схемами Zod, которые Hey API уже генерирует из контракта (`@catalog/contract/zod`). Одна общая pipe в `core/validation`; ошибки → `422 validation_failed` с `errors[]` по полям (API4). Своих DTO-классов с `class-validator` не пишем — источник правды один, контракт.
  > Примечание (2026-11-09, T-401): схема указывается в декораторе параметра — `@Body({ schema: zLoginBody }) body: LoginData['body']` (так в Nest 12, Standard Schema), проверяет своя `ValidationPipe` (`core/validation`): ей нужно исходное значение, чтобы отличить отсутствующее поле (`required`) от неверного типа, и строки адреса (`?limit=30`) она приводит к числам и логическим значениям по схеме. Без схемы в декораторе параметр не проверяется.
- **Пути и методы в декораторах** (`@Get('products/:id')`) типы не проверяют — это ловят тесты на соответствие контракту (T-413).
- **Ответы** в разработке и тестах проверяются схемами Zod ответов (ADR 0001); в продакшене — нет (скорость).

## 6. Изоляция магазинов

Главный риск для SaaS. Правила:
1. Таблицы с данными магазина имеют `shop_id` (уже в [data-model.md](data-model.md)).
2. Админские запросы: `shopId` — только из сессии, никогда из адреса или тела (API1).
3. Витрина: `shopId` получаем по поддомену в начале запроса (опубликован? превью-токен?), дальше — как в админке.
4. Каждая функция репозитория по данным магазина: `findById(db, shopId, id)`, `list(db, shopId, filter)` — `shopId` обязательный аргумент, условие `eq(table.shopId, shopId)` в каждом запросе. Поиск «по id без магазина» запрещён (кроме `auth` и `staff`).
5. В каждом модуле есть тест «чужой магазин»: магазин Б не видит и не меняет данные магазина А (ответ 404, а не 403 — не выдаём, что объект существует).
6. Row Level Security в PostgreSQL — вторая линия позже (T-606), схема это позволяет. Решение основателя 2026-11-08: не включаем в T-402 — цена (каждый запрос в транзакции с установленным `shop_id`, сложнее пул подключений, фоновые задачи и суперадминка) выше пользы, пока есть правила 4–5.

## 7. Ошибки

- В сервисах — `throw new AppError('category_has_children', 409)`; коды берём из контракта (`ProblemCode`), новый код — сначала в `openapi.yaml`.
- Не найдено → `AppError('not_found', 404)`.
- Глобальный фильтр (`core/errors`) превращает `AppError`, ошибки проверки и любые неожиданные исключения в `application/problem+json` (API4). Неожиданное → 500 `internal_error` без деталей наружу, полный текст — в лог.
- Тексты для людей не пишем: их показывает фронт по `code` (Lingui).

## 8. Транзакции

- Транзакция начинается **в сервисе**: `await this.db.transaction(async (tx) => { … })`.
- Функции репозитория принимают первым аргументом `db: Db | Tx` — тогда одна и та же функция работает и внутри транзакции, и без неё. Передаём явно, без скрытой магии.
- Сервис, вызывающий сервис другого модуля внутри транзакции, передаёт ему `tx` (у таких методов он необязательный последний аргумент).
- Обязательно в транзакции: `PUT` таблиц целиком (варианты, значения свойств, порядок), применение импорта, публикация с проверками, массовые действия.
- Фоновую задачу ставим **в той же транзакции** (pg-boss умеет работать с внешним подключением) — тогда задача не появится, если транзакция откатилась.

## 9. Фоновые задачи (pg-boss)

- Подключение и запуск — `core/jobs`. Имена задач — константы рядом с модулем: `photos.process`, `imports.parse`, `imports.apply`.
- Обработчик живёт в модуле (`modules/products/workers/process-photo.worker.ts`) и вызывает сервисы модуля — та же логика, что у HTTP.
- Для MVP обработчики работают **в том же процессе**, что и API. Если сжатие фото начнёт тормозить API — вынести в `worker.ts` отдельным процессом (код не меняется, меняется только точка входа).
- Задача должна быть **идемпотентной**: повторный запуск после сбоя не ломает данные (проверить статус перед работой).

## 10. Конфиг и окружение

- Все переменные — в одном месте, `core/config`: читаются и проверяются схемой Zod при старте; нет переменной — приложение не стартует с понятной ошибкой.
- В коде — только через сервис конфига, без `process.env` по месту.
- Каждая новая переменная — в `.env.example` и `README.md` (правило CLAUDE.md).

## 15. Решения (2026-11-08, основатель — по рекомендациям)

1. **Подход:** модульный монолит на модулях Nest с тонкими слоями (раздел 2).
2. **Слой репозитория:** отдельный `*.repository.ts` со всем SQL — ради изоляции магазинов в одном месте (а не SQL прямо в сервисах).
3. **Платформа HTTP: Express**, а не Fastify: узкое место API — база, а не HTTP-слой; на Express больше примеров, и модели реже ошибаются в деталях (cookie, заголовки). Переезд на Fastify потом — замена адаптера в `main.ts` и пары плагинов, если в коде нет типов Express (правило: `@Req()` / `@Res()` с типами Express только в `core`).
4. **Фоновые задачи:** в том же процессе, что и API; вынести в отдельный процесс — сменой точки входа, когда понадобится.
5. **Тесты на Testcontainers** (~~база из `docker compose`~~, пересмотрено в обсуждении 2026-11-08): `pnpm check` и CI сами поднимают чистую базу, не нужно помнить про `docker compose up`, тесты не зависят от данных разработки. Цена — несколько секунд на старт контейнера и Docker, который для разработки и так нужен.
6. **Row Level Security** — не сейчас, вернуться в T-606 (раздел 6).

### Принцип выбора (2026-11-08, обсуждение с основателем)
С ИИ дешевеет **написание** кода, но не **владение** им. Поэтому:
- не отказываемся от того, что дёшево написать и что **защищает** — тесты, строгие типы, линтер границ, тесты контракта, тест изоляции магазинов, проверка конфига, структурные логи;
- по-прежнему не берём то, что дорого **содержать** — больше частей в работающей системе (микросервисы, gRPC, брокер сообщений), больше слоёв и абстракций в коде: каждая лишняя абстракция — это токены в каждой сессии агента, больше мест для ошибки и больше, что основатель должен понимать на ревью.
