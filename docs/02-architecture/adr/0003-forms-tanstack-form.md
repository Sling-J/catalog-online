# 0003. Формы админки: TanStack Form

## Контекст
- До T-306 все формы админки (вход, регистрация, пароль, мастер, редактор товара) писались на `useState`: значения, ошибки по полям, снятие ошибки при правке, ошибки сервера, «есть правки» — каждая форма заново.
- Впереди тяжёлые формы: импорт с сопоставлением колонок (T-309), «О магазине» с графиком (T-310), категории и свойства (T-311). Основатель (2026-11-05): формы — на библиотеке, а не руками.
- В редакторе товара много своих полей (цена с форматированием, «− N +», выпадающие списки, правка прямо в таблице) и зависимых значений (цена по умолчанию у строк, чипы размеров по выбранным).

## Варианты
1. **Свои формы на `useState`**: без зависимостей, но одно и то же в каждой форме и поддержка руками.
2. **React Hook Form**: зрелый, большое сообщество, короткий код для обычных `<input>`. Свои поля — через `Controller`, зависимые значения — через `watch` (перерисовывает крупные куски), вложенные массивы типизированы слабее.
3. **TanStack Form**: из того же семейства, что Router и Query; подписка на отдельные значения, строгие типы путей (`rows[2].price`) и массивов полей, схемы через Standard Schema (Zod напрямую). Моложе (v1 — 2025), код полей многословнее.

## Решение
Вариант 3, `@tanstack/react-form` (точная версия в `apps/admin/package.json`). Решение основателя 2026-11-05.

Как пользуемся (код — `apps/admin/src/shared/ui/app-form`):
- Форма — `useAppForm` (обёртка над `createFormHook`): поля `form.AppField` → `field.TextField` (поле `@catalog/ui` с ошибкой), `form.AppForm` → `form.SubmitButton`, `form.FormServerError`. Свои поля — `form.Field` с render-функцией или через `useFieldContext`.
- Проверка на клиенте — `validators.onSubmit` формы: ошибки появляются после «Отправить» и снимаются правкой поля (поведение библиотеки); `invalidFields` собирает ответ.
- Ошибки сервера: у поля — `setServerError` (ключ `onServer`), всей формы — `setFormError`. Форма создаётся с `canSubmitWhenInvalid`, а отправка идёт через `submitForm`: он снимает ошибки сервера прошлой попытки, иначе повторить отправку после «нет связи» или «неверный пароль» было бы нельзя. Ошибки проверки на клиенте отправку по-прежнему не пускают.
- «Есть правки» — `useIsDirty` (значения отличаются от исходных); исходные значения передаём стабильным объектом (`useState`), иначе форма примет новый объект за новые значения.
- Логику, не зависящую от формы (проверка черновика товара, что отправить в API), держим чистыми функциями в `lib/` — их тесты не зависят от библиотеки.

Действует для `apps/admin`. Витрина (`apps/web`) — по мере появления форм.

## Последствия
- Проще: значения, ошибки, отправка и «есть правки» — у библиотеки; новые формы собираются из общих частей.
- Сложнее: поля — render-функции внутри `form.Field`, кода в разметке больше; поведение ошибок сервера держится на своей обвязке (`submitForm`, `setServerError`) — менять осторожно.
- Риск молодой библиотеки: при обновлении проверять формы входа и редактор товара (ошибки, повторная отправка, «Уйти без сохранения?»).
