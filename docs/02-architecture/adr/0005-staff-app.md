# 0005. Суперадминка — отдельное приложение `apps/staff`

## Контекст
- FR-S1–S3, D9: минимальная суперадминка для нас — список магазинов с цифрами, блокировка (D15), вход «от имени» магазина для поддержки. API готов в T-412 (`/v1/staff/*`, cookie `staff_sid`), экранов нет (T-504).
- Сотрудник и владелец магазина — разные люди с разными сессиями (`staff_sid` и `sid`), разными правами и журналом действий.
- Вход «от имени» ставил cookie `sid` тому сайту, с которого пришёл запрос. С отдельного адреса cookie попадает в админку только через общий родительский домен (`COOKIE_DOMAIN`) — в продакшене. В разработке (`staff.localhost` и `app.localhost` — разные сайты, запросы идут через прокси Vite) и в e2e так не работает.

## Варианты
1. **Раздел в `apps/admin` под отдельным входом** (`/staff`): меньше сборок и деплоев, общие компоненты. Минус: в одном приложении две сессии, два набора прав и маршрутов, код сотрудника попадает в сборку для владельцев.
2. **Отдельное приложение `apps/staff`**: логика сотрудника не смешивается с админкой магазина, своя небольшая сборка. Минус: ещё одна сборка и запись в деплое.

Вход «от имени» из отдельного приложения:
- а) **общий cookie-домен** — API не меняется, но в разработке и e2e не проверить;
- б) **одноразовый токен** — API выдаёт ссылку в админку с токеном, админка обменивает его на свою сессию.

## Решение
Вариант 2 и б (решения основателя 2026-11-15).

- `apps/staff` — SPA на Vite + React + TanStack Router и Query, компоненты `@catalog/ui`, запросы — сгенерированный SDK `@catalog/contract`. Структура — FSD, как у админки ([ADR 0002](0002-frontend-fsd.md), `frontend-structure.md`). Без Lingui (внутренний инструмент, только русский), без моков MSW (только настоящий API) и без TanStack Form (одна форма входа на два поля).
- Адрес — `staff.<домен>`; в разработке `staff.localhost:3003` (запросы через прокси Vite, как у админки), в e2e — :3103. Поисковикам закрыт (`noindex`).
- Экраны — сразу в коде, без макетов (решение основателя 2026-11-15): вход; список магазинов (поиск, название, адрес витрины, почта, статус, дата регистрации, товаров, нажатий «Заказать» за 30 дней, «Показать ещё»); действия в строке — «Войти от имени», «Заблокировать» (с необязательной причиной), «Разблокировать»; «Выйти».
- Вход «от имени»: `staffImpersonateShop` отвечает `{ url }` — ссылкой `https://app.<домен>/impersonate#<токен>`. Токен одноразовый, живёт 60 секунд, в базе — только хеш (`auth_tokens`, назначение `impersonate`, с id сотрудника). Токен — во фрагменте адреса: он не уходит на сервер в запросе страницы и в заголовке `Referer`. Админка отправляет его в `POST /v1/auth/impersonation` и получает свою сессию `sid` с отметкой сотрудника (2 часа без продления, ограничения прежние — `api.md`, «Суперадминка»). Использованный или просроченный токен — 410 `token_expired`. В журнал пишется выдача ссылки.
- Для приложения в контракт добавлены `staffMe` (кто вошёл) и `staffLogout`.
- В админке при входе «от имени» — плашка «Вы вошли от имени магазина» над шапкой, чтобы сотрудник не перепутал вкладки.

## Последствия
- Проще: код и сессия сотрудника отдельно от админки магазина; вход «от имени» одинаково работает в разработке, e2e и продакшене и не зависит от `COOKIE_DOMAIN`.
- Сложнее: ещё одно приложение в `pnpm dev`, e2e и деплое (T-602 — поддомен `staff`).
- Дальше: журнал действий (`audit_log`) пока не показывается — экран, когда понадобится.
