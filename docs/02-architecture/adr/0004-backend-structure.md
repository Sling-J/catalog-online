# 0004. Структура кода бэкенда: модульный монолит на модулях NestJS

## Контекст
- Старт E4: пишется `apps/api` (NestJS, Drizzle, pg-boss — [ADR 0001](0001-stack.md)). Код пишут агенты по задачам бэклога, часть — Sonnet по одной задаче за сессию; основатель силён во фронте, бэк проверяет по правилам. Нужны жёсткие соглашения, как FSD для фронта ([ADR 0002](0002-frontend-fsd.md)).
- Контракт уже готов: Hey API генерирует типы контроллеров по тегам `openapi.yaml` (`ProductsControllerMethods` и т. п.) и схемы Zod.
- Главный риск SaaS — данные одного магазина видны другому (NFR-4).

## Варианты
1. **Слои по техническим папкам** (`controllers/`, `services/`): просто, но фича размазана, границ нет.
2. **Модули по предметным областям** (родной путь Nest) с тонкими слоями внутри: контроллер → сервис → репозиторий.
3. **Чистая / гексагональная архитектура:** логика независима от Nest и базы, но интерфейсы и мапперы на каждую сущность — в 2–3 раза больше кода без пользы для CRUD по контракту.
4. **DDD, CQRS, вертикальные срезы, микросервисы:** избыточны для простой предметной области и одного API.

Подробный обзор с плюсами и минусами — [backend-structure.md](../backend-structure.md), раздел 1.

## Решение
Вариант 2: модуль на тег контракта, внутри — контроллер (`implements` сгенерированного типа), сервис (правила, транзакции), репозиторий (весь SQL, `shopId` обязательным аргументом), маппер; сложная логика — чистыми функциями в `lib/`; витрина — отдельный модуль только для чтения. Платформа — Express; фоновые задачи — в процессе API; тесты на настоящей базе через Testcontainers; RLS — позже (T-606).

Принцип выбора: с ИИ дешевеет написание кода, но не владение им — берём сразу всё, что дёшево написать и что защищает (тесты, типы, линтер границ, тест изоляции), и не берём то, что дорого содержать (лишние части системы и слои).

Правила — в [backend-structure.md](../backend-structure.md); это источник правды, его можно уточнять по ходу работы с согласия основателя без нового ADR, пока не меняются модули по областям, слои и правило `shopId` в репозиториях.

## Последствия
- Проще: каждый модуль устроен одинаково — новые модули делаются по образцу; изоляция магазинов проверяется в одном месте (репозитории) и тестом в каждом модуле; расхождение с контрактом ломает `tsc`.
- Сложнее: больше файлов на модуль; межмодульные вызовы только через экспортированные сервисы; `tx` передаётся явно.
- T-401: каркас по этой структуре, линтер границ для `apps/api`, Vitest с SWC, Testcontainers, точные версии пакетов из раздела 14.
