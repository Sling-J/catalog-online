# 0001. Стек и устройство приложения

## Контекст
- Основатель пишет на TypeScript; код дальше поддерживает он вместе с ИИ, поэтому объём шаблонного кода не аргумент, а структура и соглашения — аргумент.
- Процесс: сначала контракт API, фронт пишется против моков, потом бэк (`06-process/workflow.md`). Значит, API отдельный, контракт — файл в репозитории.
- Публичная часть: лендинг на основном домене и витрины на поддоменах (`<поддомен>.<сервис>.kz`). Нужны SSR, SEO и превью ссылок в WhatsApp/Instagram (NFR-2, NFR-5).
- Админка — закрытый рабочий инструмент за логином, SSR и SEO ей не нужны.
- Импорт Excel/CSV до 20 000 строк, фото до 15 МБ (в т. ч. HEIC) со сжатием в несколько размеров (FR-A3, FR-A4) — тяжёлая работа идёт в фоне.
- Где хранить данные — не решено (закон РК о персональных данных, см. open-questions). Инфраструктура должна легко переезжать между хостингами.
- Пилот: 2–5 магазинов, до 100 без деградации (NFR-3). Бюджет минимальный.

## Варианты (кратко, что обсуждали)
- **Фронт-проекты:** один Next на всё / публичная часть и админка отдельно. Выбрано отдельно: разные задачи (SSR и SEO против рабочего SPA), код админки не попадает в публичную часть, независимые деплои.
- **Публичная часть:** Next.js / TanStack Start. Выбран Start: загрузчики маршрутов работают и на сервере, и на клиенте — при переходах клиент ходит прямо в наш API, сервер фронта нужен только для первой страницы; SSR настраивается по маршруту; типизированные search params роутера.
- **Бэкенд:** Fastify / NestJS / Hono. Выбран NestJS: модули, DI и соглашения окупаются, шаблонный код пишет ИИ.
- **База:** PostgreSQL + Drizzle / Prisma. Выбран Drizzle: типы и SQL под контролем, миграции файлами.
- **Монорепо:** только pnpm workspaces / Turborepo / Nx. Выбран Turborepo поверх pnpm: порядок сборки и кеш одним файлом, без тяжести Nx.

## Решение

| Слой | Выбор |
|---|---|
| Пакетный менеджер и монорепо | pnpm workspaces + Turborepo (без облачного кеша на старте) |
| Структура | `apps/web`, `apps/admin`, `apps/api`, `packages/ui`, `packages/contract` |
| Контракт API | OpenAPI 3.1 `packages/contract/openapi.yaml` — источник правды, пишется руками |
| Генерация из контракта (дополнено 2026-10-31) | Hey API (`@hey-api/openapi-ts`), точная версия зафиксирована. Для фронтов: типы, SDK, хуки TanStack Query, схемы Zod, моки MSW. Для бэка: плагин NestJS — типы методов контроллеров, контроллеры их `implements`. Сгенерированное лежит в `packages/contract` (`*.gen.ts`, руками не правим), задача `generate` в Turborepo идёт перед проверкой типов и сборкой. Расхождение с контрактом ломает проверку типов в CI. Не ловит: пути и HTTP-методы в декораторах Nest (ловят тесты API) и фактическую форму ответа во время работы (проверка ответов через Zod в разработке и тестах) |
| `apps/web` — лендинг и витрины | TanStack Start (React, SSR при первой загрузке, дальше SPA). Поддомен магазина определяется в глобальном request middleware по заголовку `Host` |
| `apps/admin` — админка | Vite + React SPA, TanStack Router (без Start, SSR не нужен) |
| Серверное состояние (оба фронта) | TanStack Query |
| Формы (админка, дополнено 2026-11-05) | TanStack Form — [ADR 0003](0003-forms-tanstack-form.md) |
| Перетаскивание (админка, дополнено 2026-11-05) | `@dnd-kit/react` + `@dnd-kit/helpers` (точная версия 0.5.3, ветка 0.x — обновлять осознанно): касание с задержкой, клавиатура, сортировка сеткой. Решение основателя (T-307, фото товара); дальше — порядок категорий и свойств |
| Клиентская бизнес-логика и стейт | Effector — только там, где нужен (например, корзина). На сервере без глобальных сторов: либо только клиент, либо `fork`-scope на запрос |
| Фильтры, категории, сортировка | В URL через search params роутера (FR-V4), не в стейт-менеджере |
| Локализация | Lingui (Vite-плагин, макросы при сборке, PO-каталоги). На сервере — свой экземпляр `i18n` на каждый запрос |
| Шрифт | Geologica со своего сервера: пакет `@fontsource-variable/geologica` (вариативный, кириллица с казахскими буквами), кириллица — `preload`. Без запросов к Google Fonts (решение основателя 2026-11-02) |
| Общие пакеты | `packages/ui` — токены из `DESIGN.md` и базовые компоненты; `packages/contract` — OpenAPI и сгенерированные типы |
| Стили | Tailwind CSS с токенами из `DESIGN.md` |
| Превью витрины в админке | iframe настоящей витрины из `apps/web` в режиме черновика; несохранённые изменения передаются через `postMessage` |
| Бэкенд `apps/api` | NestJS (TypeScript) |
| База | PostgreSQL + Drizzle ORM, миграции файлами |
| Фоновые задачи | pg-boss (очередь в той же PostgreSQL, без Redis) — подключается в Nest своим провайдером |
| Фото | S3-совместимое хранилище (на VPS — MinIO); сжатие и размеры — sharp в фоновой задаче |
| Excel/CSV | ExcelJS для `.xlsx`; csv-parse + iconv-lite для CSV (UTF-8 / Windows-1251) |
| Авторизация | Email + пароль, сессия в HttpOnly-cookie, сессии в PostgreSQL, хеш argon2. Админка на `app.<сервис>.kz`, API на `api.<сервис>.kz`, cookie и CORS настраиваются под общий родительский домен |
| Письма | SMTP-провайдер (выбор — открытый вопрос) |
| Тесты | Vitest (юнит, API), Playwright (сценарии в браузере) |
| Среда выполнения | Node.js 22 LTS или новее (Lingui 6 требует ≥ 22.19, только ESM) |
| Инфраструктура | Docker Compose на одном VPS: web, admin (статика), api, worker, postgres, minio, Caddy (HTTPS, wildcard-сертификат для поддоменов) |

Хостинг (КЗ или за рубежом) — отдельный ADR после ответа о локализации данных. Стек от этого не зависит.

> Примечание (2026-11-01): образы MinIO убраны с Docker Hub. В разработке вместо него SeaweedFS (тот же S3 API, `docker-compose.yml`); хранилище для продакшена выбираем вместе с хостингом — open-questions, T-601. Решение по S3-совместимому хранилищу при этом не меняется.

> Примечание (2026-11-01, T-102): магазин по поддомену определяется не в глобальном request middleware, а изоморфной функцией (`apps/web/src/app/lib/get-tenant.ts`): на сервере читает заголовок `Host`, в браузере — `location.host`; результат кладётся в контекст роутера в `beforeLoad` корня. Причина: middleware выполняется только на сервере (первая загрузка), а при переходах на клиенте магазин нужно знать тоже; с middleware пришлось бы держать два пути (контекст через `handler.fetch(request, { context })` на сервере и чтение `location.host` на клиенте), а `beforeLoad` одинаково работает в обоих случаях. Решение «магазин определяется по `Host`» не меняется.

> Примечание (2026-11-02, решение основателя): таблицы админки (товары, размеры в редакторе, импорт) делаем своими компонентами без библиотеки — сортировка, поиск и фильтры на сервере, вёрстка по макетам своя. Общие куски — `shared/ui` админки. Если понадобится виртуализация длинных списков — `@tanstack/react-virtual`, если колонки по выбору или клиентская сортировка — TanStack Table (оба безголовые, того же семейства).

> Примечание (2026-11-08, T-315, по поручению основателя «делай, как считаешь правильным»): сценарии в браузере (строка «Тесты» выше) — пакет `tools/e2e` с `@playwright/test` (devDependency, та же версия, что `playwright-core`), тоже с установленным Google Chrome (канал `chrome`), браузеры не скачиваются. Запуск — `pnpm e2e`, в `pnpm check` не входит: нужен Chrome и поднимается дев-сервер админки на моках (порт 3022). Решение «Playwright для сценариев» не меняется.

> Примечание (2026-11-02, решение основателя): для сверки экранов с макетами — `playwright-core` (только в `tools/design-compare`, devDependency) с установленным Google Chrome; браузеры playwright не скачиваются. В приложения не попадает.

## Последствия
- Проще: один язык и одна экосистема (TanStack) на обоих фронтах; общий контракт и общие пакеты; всё переносится контейнерами; нет платных облачных зависимостей.
- Сложнее:
  - TanStack Start моложе Next — стабильную версию фиксируем при создании репозитория и сверяем документацию через Context7.
  - Контракт пишется руками до кода; бэкенд не генерирует спецификацию, а реализует сгенерированные из неё типы (Hey API, плагин NestJS). Пути и методы в декораторах проверяются тестами API.
  - Hey API активно развивается — версию фиксируем точно, обновляем осознанно.
  - Drizzle и pg-boss в Nest подключаются своими провайдерами (готовых официальных модулей нет).
  - Инфраструктуру (бэкапы, обновления, мониторинг) ведём сами; wildcard-сертификат требует DNS-провайдера с API.
- Дальше на стадии 3: модель данных (`02-architecture/data-model.md`), контракт API (`packages/contract/openapi.yaml`), ADR по хостингу.
- Если основатель передумает по какому-то пункту — новый ADR, заменяющий соответствующую часть.
