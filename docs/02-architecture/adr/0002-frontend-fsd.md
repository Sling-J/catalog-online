# 0002. Структура кода фронтенда: Feature-Sliced Design

## Контекст
- Старт E1: пишется `apps/web`, затем `apps/admin`. Код поддерживает основатель вместе с ИИ, поэтому нужны жёсткие, проверяемые соглашения о том, где что лежит и кто кого может импортировать (ADR 0001: структура и соглашения — аргумент).
- У основателя есть отработанный набор правил на FSD из другого проекта (React Native + Effector).

## Варианты
1. **Свободная структура по типам файлов** (`components/`, `hooks/`, `store/`): быстро на старте, но зависимости быстро запутываются.
2. **Классический FSD** с правилом `@x` для перекрёстных импортов между сущностями: гибко, но стирает границы срезов.
3. **FSD с правилами основателя**: слои сверху вниз, никаких импортов между срезами одного слоя (общее выносится ниже), модель только Effector, `api/` отдельно, доступ к срезу через его `index.ts`.

## Решение
Вариант 3. Правила и их адаптация к проекту (React DOM, TanStack Start/Router, Query, сгенерированный SDK, `@catalog/ui` как часть `shared`, файлы маршрутов в `app`) — в [frontend-structure.md](../frontend-structure.md); это источник правды, его можно уточнять по ходу работы с согласия основателя без нового ADR, пока не меняются слои и запрет импортов между срезами.

Действует для `apps/web` и `apps/admin`. `apps/api` не касается.

## Последствия
- Проще: понятно, куда класть код; границы проверяются линтером; общий код вытесняется вниз и не дублируется.
- Сложнее: больше папок и `index.ts`; общую модель двух срезов приходится выносить в нижний слой заранее; файловый роутер Start приходится держать тонким слоем в `app`.
- Нужна настройка линтера границ (T-100) — выбор инструмента согласуем отдельно.
