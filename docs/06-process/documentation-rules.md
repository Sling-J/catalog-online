# Правила ведения документации

Документы — память проекта: у агента нет памяти между сессиями, и решение, которого нет в `docs/`, считается не принятым. Поэтому документы должны быть точными, а точность держится на двух вещах: каждый факт записан в одном месте, и расхождения ловит проверка, а не внимательность.

## 1. Один факт — одно место

Каждый факт живёт в одном документе, остальные на него ссылаются, а не пересказывают. Пересказ — место, которое забудут обновить.

| Факт | Где живёт | Чего не делаем |
|---|---|---|
| Где проект сейчас и что дальше | [status.md](../status.md) | не пишем состояние в оглавлениях и README разделов |
| Что сделано по задаче, решения по ходу, как проверено | [changelog.md](../changelog.md) | не пишем заметки «что сделано» в бэклоге |
| Список задач и что закрыто | [backlog.md](../05-tasks/backlog.md): галочка и одна строка | — |
| Решение по теме | таблица решений своего документа (D, S, A, API, DM…) или ADR | не перечисляем диапазоны номеров («A1–A8») в других местах |
| Статус документа | front matter самого документа | не дублируем в оглавлениях (кроме журнала ADR — там статус часть формата) |
| Нерешённое | [open-questions.md](../open-questions.md) | — |

## 2. Оформление

1. **Front matter** в каждом тематическом документе: `status` (`draft` → `review` → `accepted` → `outdated`), `owner`, `updated` (дата последней правки). Без него — `README.md` разделов (это оглавления) и `status.md` (только текущее).
2. **Один файл — одна тема.** Разрастается больше ~300 строк — делим.
3. **Именование:** латиница, `kebab-case`; разделы с номерами `00-`…`06-` — номер задаёт порядок чтения ([../README.md](../README.md)).
4. **README в каждом разделе** — оглавление: только существующие файлы со ссылкой и одной строкой «что внутри». Чего ещё нет — одной строкой «Позже: …» без имён файлов. Тема описана в другом документе — так и пишем со ссылкой.
5. **Ссылки** относительные, markdown-ссылками; между документами ссылаемся, а не копируем текст.
6. **Язык:** русский; код, идентификаторы и принятые термины можно на английском.

## 3. Решения и изменения

1. **Архитектурные решения** — ADR (`02-architecture/adr/NNNN-название.md`, номер сквозной, `0000` — шаблон). Принятый ADR не переписывается: новое решение — новый ADR, старый получает `superseded by NNNN`.
2. **Продуктовые и экранные решения** — в таблице решений своего документа, с датой.
3. **Принятые (`accepted`) документы** меняются только с согласия основателя. Фактическая поправка (устаревшая ссылка, переименованный файл) — примечанием с датой.
4. **Изменилось решение** — старое зачёркиваем со ссылкой на новое, а не удаляем; ищем и правим все упоминания.
5. **Факт против гипотезы:** гипотезы помечаем («гипотеза», «предварительно»); проверенное — с источником (интервью, замер).
6. **Открытый вопрос** живёт в [open-questions.md](../open-questions.md); решён — ответ переезжает в профильный документ или ADR, вопрос отмечается `[x]` со ссылкой.
7. **Устаревший документ** не удаляем сразу: `status: outdated` и ссылка на актуальный.

## 4. Автоматическая проверка

`pnpm docs:check` (входит в `pnpm check`, скрипт — `tools/docs-check`) проверяет:
- относительные ссылки ведут на существующие файлы;
- у тематических документов в `docs/` есть front matter с `status`, `owner`, `updated` и допустимым статусом;
- README каждого раздела ссылается на все документы раздела и не ссылается на несуществующие;
- статусы в журнале ADR совпадают с front matter самих ADR.

Что проверка не ловит — противоречия по смыслу (два документа говорят разное). Это на ревью: перед коммитом документы не противоречат коду и друг другу ([CLAUDE.md](../../CLAUDE.md)).
